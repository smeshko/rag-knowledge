01 The problem RAG solves

A brilliant intern
with no files.

An LLM only knows what it absorbed during training. Brilliant, but frozen in time, blind to your private data, and willing to make things up with total confidence.

Picture a razor-sharp intern who read most of the public internet two years ago, then got locked in a room with no phone and no filing cabinet. Ask about last quarter's revenue and they'll confidently invent a number — because nothing in the room tells them otherwise.

That confident invention has a name: hallucination. It is not a bug you can prompt away; it is what a model does when it has no grounding. Three failure modes follow directly:

› Stale knowledge. Training stopped on a date. Anything after it — or any private doc — simply doesn't exist to the model.

› Hallucination. Asked something it doesn't know, it produces fluent, plausible, wrong text rather than admitting ignorance.

› No provenance. Even a correct answer can't be traced to a source you trust.

The one-sentence idea

RAG turns a closed-book exam into an open-book exam. Before the model answers, we retrieve the most relevant passages from a library we control and paste them into the prompt. The model's job shifts from "recall from memory" to "read these notes and answer." That's the whole trick — and why it's called retrieval-augmented generation.

02 The big picture

Two phases,
seven moves.

Every RAG system splits cleanly into work you do ahead of time (offline) and work you do per question (online). Mixing them up is the #1 source of confusion.

◆ Phase A — done once, offline

Index your knowledge

  1. Ingest — pull text out of PDFs, docs, pages, transcripts
  2. Chunk — slice documents into bite-size passages
  3. Embed — turn each chunk into a vector of meaning
  4. Store — save vectors + text + metadata in a vector store
● Phase B — done per query, online

Retrieve & generate

  1. Embed the question with the same model
  2. Retrieve the most similar chunks (the search)
  3. Augment — paste those chunks into the prompt
  4. Generate — the LLM answers from the supplied context

Laid end to end, the seven moves form the pipeline every section below zooms into. Almost every "advanced RAG" technique is just a smarter version of one of these boxes.

Key tension to remember: give the model too few chunks and it misses the answer; give it 20–50+ chunks and you overwhelm it — accuracy drops and cost climbs. The entire retrieval craft is about handing over few chunks, but the right ones.
03 Chunking

Cut the book into
index cards.

You can't embed a whole 80-page report as one vector — the meaning blurs into mush and you'd shove the entire thing into the prompt. So you split it into passages. How you split decides how good retrieval can ever be.

ELI5

Imagine ripping a textbook into flashcards. Rip on random character counts and a card might end mid-sentence, splitting one idea across two cards. Rip along natural seams — paragraphs, sections — and each card holds one whole thought. Same book, wildly different study results.

StrategyHow it cutsTrade-off
Fixed-sizeEvery N characters/tokens (e.g. ~1,000), often with a little overlap so ideas spanning a boundary aren't lost.Dead simple & fast. Ignores structure — happily slices mid-sentence.
Context-aware ★ default pickSplits on natural boundaries (sentences, paragraphs, headings). The Docling library's "hybrid chunking" does this out of the box.Clean starts & ends. A bit more setup — "very, very worth it."
Contextual retrievalAn LLM prepends a sentence to each chunk explaining how it fits the whole doc, then embeds them together. (Anthropic technique.)Big retrieval gains. One LLM call per chunk — slow & costly to build.

Practical default: reach for context-aware (hybrid) chunking first. Layer the fancier strategies in only when evals say retrieval is your bottleneck.

04 Embeddings

Meaning, turned
into coordinates.

An embedding is a list of numbers — a vector — that encodes what a piece of text means. Texts about similar ideas land near each other; unrelated texts land far apart.

Think of a giant map where every sentence gets a pin. "Cheap flights" and "affordable airfare" use no shared words, yet sit almost on top of each other — because an embedding model placed them by meaning, not spelling. "Berlin → Germany" mirrors "Paris → France" as the same little jump across the map.

The catch: this map isn't 2-D. A modern model like OpenAI's text-embedding-3-small places each chunk in 1,536-dimensional space. We can't picture 1,536 axes — but the math of "what's nearby?" works exactly the same.

A vector is just an ordered list of numbers, e.g. [0.013, −0.21, 0.08, … ]. "Embedding" = the vector a model assigns to a chunk of text.

⚠ Golden rule: the model you use to embed your chunks must be the same one you use to embed the query. Different models draw different maps — pins from two maps can't be compared. The vector dimension is fixed by the model and must match your storage column exactly.

Pro move — fine-tuning. Train the embedder on your domain (legal, medical) and a small open model can beat a giant generic one, with 5–10% accuracy gains. Costs training data + upkeep.
05 The vector store

A table that searches
by closeness.

A vector store is just a database table where one column holds the embedding. Its superpower: given a query vector, it returns the rows whose vectors are nearest — fast, even across millions of rows.

It's less exotic than it sounds. A normal Postgres table with one extra vector column is a vector store. Here's the shape — the embedding is shortened so it fits:

How "nearest" is measured

You need a number for how close two vectors are. The workhorse is cosine similarity — the angle between two vectors, ignoring their length. Identical meaning → 1.0.

In practice Postgres reports cosine distance = 1 − similarity, ranging 0 → 2, where lower is closer. (Dot product and Euclidean distance are alternative metrics; cosine is the common default for text.)

top-k: you almost never want all matches — just the k closest, e.g. the top 3–10 rows. That's the "k" in nearest-neighbour search.

The index makes it fast

Comparing the query to every row exactly (brute force) is fine for thousands of rows. At scale you add an ANN index — Approximate Nearest Neighbour — trading a sliver of accuracy for huge speed:

  • HNSW — a navigable graph of vectors; the popular default.
  • IVFFlat — bucket vectors into clusters, search only nearby buckets.
  • StreamingDiskANN — disk-friendly index from pgvectorscale; great when data outgrows RAM.
You may not need a dedicated vector DB

Pinecone, Weaviate and Qdrant are purpose-built vector databases — but PostgreSQL + the pgvector extension turns one ordinary database into a vector store that's "in most cases just as good." Keeping embeddings and your app's relational data in one place is a big operational win. Reach for a specialised DB mainly at the billions-of-rows scale.

-- semantic search in plain Postgres + pgvector
SELECT id, content, embedding <=> :query_vec AS distance
FROM chunks
ORDER BY embedding <=> :query_vec -- <=> is cosine distance
LIMIT 5; -- top-k = 5
06 Retrieval & hybrid search

Meaning vs. exact words
— you need both.

Semantic (vector) search is magic for concepts. But it quietly fumbles exact tokens: product codes, error numbers, names, a specific year. The fix isn't a better embedder — it's a second search that speaks "keywords."

● Semantic / dense search

Compares meaning via embeddings. Finds "earnings" when you typed "revenue"; finds the right doc even with zero shared words.

✗ Misses: 409 error, SKU AAPL, "the 2025 figure" — exact tokens get blurred into nearby concepts.

● Keyword / lexical search

Classic full-text matching, scored by BM25 (an upgraded TF-IDF: term frequency × rarity). Guaranteed to find an exact term if it's there.

✗ Misses: paraphrases & synonyms — ask in different words than the doc uses and it returns nothing.

They fail in opposite places — "dense wins exactly where BM25 loses, and loses exactly where BM25 wins." So hybrid search runs both and merges. Try it: pick a search mode and watch which chunks each retrieves for the same query.

Neuroflow revenue 2025
doc: financials_q4.pdf"Neuroflow's 2025 full-year revenue reached $4.2M, up 35%."✓ exact tokens "Neuroflow", "2025", "revenue" AND on-topic meaning → the bullseye.
doc: annual_2023.pdf"In 2023, Neuroflow reported annual revenue of $3.1M."⚠ keyword loves "Neuroflow/revenue", semantic loves the topic — but it's the wrong year. Why rerank matters.
doc: board_notes.md"Total fiscal-year earnings for the company grew significantly."✓ semantic only — "earnings" ≈ "revenue" with no shared keywords. Keyword search misses this entirely.
doc: product_blog.md"Neuroflow launched a new developer SDK this March."⚠ keyword only — matches "Neuroflow" but is about a product launch, not money. Noise.
doc: support_kb.md"Customer churn dropped to 2% after the redesign."

Step 2 — fuse the two lists

Semantic scores (0–1) and BM25 scores (e.g. 11, 13, 15) live on different scales — you can't just add them. Reciprocal Rank Fusion (RRF) sidesteps that by ignoring raw scores and using only each doc's rank position:

# each list contributes, per document:
score = 1 / (k + rank) # k = 60, the classic default
# a doc's final score = sum across both lists

Docs ranking high in both lists float to the top. Simple, parameter-light, shockingly effective.

Step 3 — rerank for the final cut

A reranker is a cross-encoder: it reads the query and a candidate together, scoring true relevance far more accurately than the first-pass retrieval. Too slow for millions of docs — perfect for re-scoring your top ~50.

Bi-encoder (embeddings): query & doc encoded separately → fast, used to retrieve.
Cross-encoder (reranker): encoded together → slow, accurate, used to re-sort. Cohere Rerank is a common pick.

Measured impact, one finance dataset (NDCG@10): BM25 alone ≈ 28 · hybrid (RRF) landed between dense and BM25 · hybrid + reranker = 47. The reranker was the single biggest lever — but on this data, plain dense beat naive hybrid. Lesson: measure on your own corpus; don't assume the full stack wins.

08 Agentic RAG

From assembly line
to detective.

Naive RAG retrieves once, then answers — the model's intelligence is used a single time, on whatever chunks it was handed. Agentic RAG hands the model the search tools and lets it investigate in a loop.

Naive RAG

linear · one pass · force-fed
Query → embed
Retrieve top-k (fixed)
Stuff into prompt
LLM answers — once

Fast, cheap, predictable. Can't recover if the first retrieval misses.

Agentic RAG

loop · multi-step · self-correcting
Query → the agent reasons
↻ repeat until satisfied
Choose tool: semantic? keyword? read whole doc?
Write its own search query
Read results → "enough? or search again?"
Answer, grounded in what it found

Because the agent writes its own queries and decides when to stop, it can rephrase, drill down, consult multiple sources, even decide not to retrieve. The common patterns:

  • Routing — pick the right source per question (graph vs vector vs web).
  • Query rewriting — turn a messy question into a clean search.
  • Iterative retrieval — search, read, search again.
  • Self-reflection — grade results, retry if weak.
The three primitive tools. Production agentic RAG over documents often needs just list_files, grep (search), and read_file — the same trio coding agents like Claude Code use to navigate a repo. The tool's docstring is part of the prompt: it's how the agent knows what to search for.
The cost. One question can fire 5+ tool calls and take 10–15s. Agentic generally beats naive on quality — but you pay in latency and tokens. Start naive for raw speed; go agentic when accuracy matters more than milliseconds.
09 Knowledge graphs · "RAG 2.0"

When the answer
lives in the connections.

Vector search finds facts about one thing. But "how are OpenAI and Microsoft related?" is a question about a relationship — and that's what a knowledge graph stores natively.

A knowledge graph represents information as entities (nodes) joined by relationships (edges): "Amazon — invested in → Anthropic", "OpenAI — hosted on → Azure". To build it, an LLM reads your raw docs and extracts every entity and link.

"RAG 2.0" stores the same documents both ways — in a vector store and a graph — and lets an agent route:

  • Vector → single-entity lookups ("Google's AI initiatives?")
  • Graph → multi-hop & relational ("how do A and B connect?")
The trade-off is build cost. Querying a graph is fast — but constructing it is slow & expensive: every chunk needs LLM extraction. One small doc (7 chunks) took ~2 minutes to graph vs seconds to embed. Tools: Graphiti on Neo4j.
10 Grounding & trust

Don't trust the answer.
Verify the source.

RAG reduces hallucination — it doesn't abolish it. A model can still answer from a chunk that doesn't actually contain the fact, and citations can be fabricated too. So serious systems prove their grounding.

Make the model confess

A cheap, powerful guardrail: force the LLM to return structured output with an enough_context boolean — "did the supplied chunks actually contain the answer, yes or no?" If false, route to a human instead of letting it improvise.

class Answer:
  thought_process: list[str] # chain of thought
  answer: str
  enough_context: bool # ← honesty flag
  citations: list[Citation] # file · quote · line

Human-in-the-loop sources

The strongest pattern: retrieval surfaces candidate chunks to the user, who approves or rejects each one. Only approved chunks are passed to a second "synthesize" step. The agent literally cannot answer from sources you didn't bless.

Why citations alone fail: an LLM can invent a plausible-looking citation just as easily as a fact. Showing the actual retrieved passage — and letting a human confirm it — is verification; a footnote is not.
11 Evaluation

If you can't measure it,
you're tuning by vibes.

RAG has two places to fail — retrieval (wrong chunks) and generation (bad answer from good chunks). Without evals you can't tell which broke, and every fix risks silently breaking something else.

Did retrieval find the right docs?

Precision & recall, hit-rate, and NDCG@10 — the gold-standard ranking metric (0–1, higher is better; rewards putting the right doc near the top). Needs ground-truth: (question → relevant doc) pairs.

Was the answer good?

Faithfulness (grounded in the chunks, not invented), answer relevance, correctness, tone. Often no single right answer — so you score with an LLM-as-a-judge.

Build it in three layers — cheap & constant at the bottom, expensive & rare at the top:

1

Unit tests

run on every change · cheap · deterministic

Plain asserts on structured output: is the category valid? is confidence a float in 0–1? did it produce a non-empty reply? Catches regressions instantly.

2

Human review → aligned LLM-judge

weekly · costlier

First you look at lots of real outputs (an Excel sheet goes a long way). Then encode that judgment into an LLM judge — and align it: compare judge vs human on the same examples, compute an agreement score, refine the judge prompt until they match. Use a powerful model, ask for a critique, not just a score, start with binary 1/0.

3

A/B testing

major releases · real users

Ship variants to real traffic; measure task completion, satisfaction, business outcomes. Highest cost, highest signal — reserve for mature systems.

The discipline that separates demos from products

No labelled data of your own? Generate a synthetic eval set: feed each doc to an LLM and ask, "write a realistic question a user would ask that this document answers." Now you have (question → doc) pairs to score retrieval against. As one principal engineer put it — looking at real traces a few hours a day "has the highest value-to-prestige ratio" in the whole field.

12 Putting it together

Start simple.
Earn the complexity.

You now have the whole map. The mistake is reaching for the fanciest technique first. The winning move is the opposite — ship the simplest thing, measure it, and add a dial only when evals demand it.

A sane build order

1 · baselineContext-aware chunking → embed → Postgres + pgvector → semantic top-k → stuff prompt. Ship it.
2 · measureBuild an eval set (synthetic is fine). Track NDCG@10 + a faithfulness judge. Now you know what's actually broken.
3 · add hybridBolt on keyword/BM25 + RRF when exact terms (codes, names, years) are getting missed.
4 · add rerankDrop in a cross-encoder reranker — usually the biggest single quality jump.
5 · go agenticLet the model drive search / add a knowledge graph only when relational, multi-hop questions appear.
